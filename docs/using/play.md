# Play

Play runs the game inside the editor, in the Game tab next to the Scene tab, the way Unity does. F5 (or the play button in the middle of the toolbar) plays the scene that is open, and Shift+F5 (the button beside it) plays from the project's start scene, as Godot's play does. The toolbar turns blue while the game runs, to say that what is changed now will not be kept. Play brings the Game tab to the front, and Stop puts back the tab it covered, unless another tab was chosen while the game ran, in which case that one stays.

The game is the real one: its own code, physics, audio and every scene it loads. It runs in a process of its own, the project's editor player started in play mode, so the first Play after the engine or the project's code changed builds that player first, in a window that shows the steps, and a game that crashes never takes the editor with it. The project needs an `editor.hxml`, which the Project Manager's projects have. The game's log goes to the Console tab, which comes to the front when the game is built or run.

The Game tab shows the game at its display's size, and while the game is not running it shows the open scene as the game would draw it, through the cameras the scene names and at the display's size on the selected platform, which follows the edits. The scene view and this preview share one player, so with both on screen at once the scene view is the one that is drawn. The first dropdown scales it (Fit, 1x, 2x, 3x), the second sets how many frames a second the game runs at, and Stats adds the time spent updating and drawing, the number of nodes and a graph of the frame time over the last half minute. Over the corner there is always the frame rate, large and colored (green from 55, amber from 30, red below), and the milliseconds a frame takes. The rate is the project's own by default, which is its default frame rate or, when the project waits for vsync, the refresh rate of the screen the editor is on, and it can be held to 30, 60, 120 or 240 or let free with Unlimited. A project with no default frame rate runs at the screen's rate too, and a game at the screen's rate draws one frame each time the editor shows one, as a built game waits for its screen. Unlimited shares the graphics card with the editor, which can then draw less smoothly. The numbers are the PC's own: a console is slower than this machine. Where it says what to do, a click on the game gives it the keyboard, Escape takes the keyboard back and Shift+Escape is the game's own Escape. The mouse is the game's while the pointer is over it, and gamepads work as they do in any game.

The Scene tab and the inspector follow the game while it runs: the nodes that are in the scene file show where the game has put them and the values it has given them, a few times a second, so the selection and the handles work on the running world and the inspector shows a moving node's position as it changes. What the game's code makes by itself, such as nodes it creates, is not in the scene, and pictures, fonts and references are not updated. When the game goes to another scene, the hierarchy, the scene view and the inspector show that scene, as Unity's hierarchy does, in the view mode (2D or 3D) the editor remembers for it, and they go back to the scene that was open when the game comes back to it or stops. The scene is read from its file, as the game does, so edits made to it while the game runs are taken back with the rest.

Keys go to the game only while the Game tab has the focus, so a node can be watched in the Scene tab but not played from it.

The scene can be edited while the game runs. A change in the inspector or the hierarchy reaches the game as it is made, so a color or a speed can be tried on the running game. When the game stops, every change made while it ran is undone, which is why the scene cannot be saved, changed for another or built while it runs. Changing a node's class is the only edit the running game does not get, and it waits for the next run.

Pause (F7, next to the play buttons) freezes the game: its scenes stop updating, the physics stops and the music is silenced, while the Game tab goes on drawing and the editor goes on working with it, so a node can be picked and its values read as they were when the game stopped. Next Frame (F10, enabled while paused) lets one frame through, in which the game's time moves by one physics step. The speed menu that shows while the game runs (1/16x to 16x) sets how fast the game's time goes, on top of the game's own `Time.timeScale`, and is remembered from one run to the next. The game's real time keeps going while it is paused, which is what `Time.unscaledDeltaSeconds` reads.

Stop (the same button, or F5) ends the game. File > Build and run (Ctrl+B) is the other way to play: it saves the scene, builds the project's game for the PC in its `build/` folder, which needs the same tools as the Project Manager's build, and runs it in a window of its own, to try what is shipped. Its log is `fried-editor-game.log` in the temporary directory.

A build, of the player or of the game, opens a window with its step, a bar and the end of its log, and a failed one stays open with the error until it is closed. Ctrl+S saves the scene to `assets/scenes/` in the project.

The Console tab shows the log while the game builds and after it runs. It follows the file as it is written, drops the terminal colors, and colors the lines: errors in red and warnings in yellow, by the level the engine prints or by what the build tools say. The Errors, Warnings and Output buttons hide each kind, the field searches, Copy puts the lines on view on the clipboard and Clear forgets them. The tab carries the number of errors, and it keeps the last ten thousand lines.
