# Project and player settings

The settings and the build output open as windows of their own, which can be moved outside the editor, onto another monitor, and closed with their own close button. On Linux the editor asks SDL for X11 so this works under Wayland too (through XWayland); set `SDL_VIDEODRIVER` to choose another driver, in which case the windows stay inside the editor if that driver cannot make windows of its own.

As in Unity, the settings are in two windows. Edit, Project Settings holds what the game is: the start scene, the autoloads, the display, vsync, the frame rate the game starts at and the physics rate. File, Player Settings holds what the builds are made of: the name, organization, version and window title, the platforms it builds for, and a page for each platform. The Project Manager edits the same file. Each change is written to `project.fried` as it is made, and the viewport's frame follows the display at once.

The platforms are ticked on the General page of Player Settings, all of them until the project narrows them. The engine refuses to configure a build for one that is not ticked, and checks the limits of the ones that are, such as an image too large for the 3DS or the DS, even in a build for another platform. At least one has to stay ticked.

Player Settings has a page for each platform that is ticked, with its icon, which is made from any image dropped on it or named by its path and converted to what that platform reads, the text its package shows, and its build: the configuration, the build folder, whether the toolchain is installed, what is wrong with the assets for that platform and a button that builds the game for it, with the output coloured as it is printed and a way to stop it. The way each platform is built is remembered for each project.

The autoloads are node classes of the project, as a Godot script is, or scenes, which the game loads once when it starts and keeps while it runs, in the order listed, for what the whole game needs, such as music or a debug overlay. Either is added from the list of what the project has, and each can be moved up or down or removed. They are not shown in the hierarchy, since they only exist while the game runs.

## Input Map

The Input Map tab edits the `input` block of `project.fried`, laid out in three columns: the maps on the left, the actions of the chosen map with their bindings under each in the middle, and the properties of what is chosen on the right. A map has a name and is switched on at start or not. An action has a name, a type (button, value or vector2) and, for the first two, the threshold a gamepad axis has to pass to count as a press. A binding is a single source, an axis made of two, a vector made of four, or a stick; the type of the action decides which of them it takes, and a binding the new type does not take is removed when the type changes. Click a source and press a key, or choose a key, mouse button, gamepad button or axis from the list, which comes from the engine so it is always the names the build accepts. Every change is saved at once, and a game that is running takes it without a build. The right click menu of a map, an action and a binding has Delete, and an action also has Duplicate and Add Binding.
